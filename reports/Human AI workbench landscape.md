# Turn AI sessions into lasting workbenches

Research checked November 10, 2026.

**Yes—there are several close parallels to SPACE, and DeepSeek Harness has relevant plugins.** AionUi and CloudCLI connect coding-agent sessions to project files and visible outputs; LibreChat and Open WebUI provide interactive artifact surfaces; marimo connects analysis to dashboards, reports and slides. Claude Code itself now publishes versioned interactive artifacts, while Claude Data provides a separate connected-data experience. DSH offers file-workbench and artifact plugins, but these do not establish a complete replacement for SPACE’s question, decision, evidence and Studio model. The practical recommendation is to **extend SPACE’s existing session, Studio and Delivery surfaces with cross-harness provenance and result registration**. This report distinguishes documented capabilities from proposed integration; no evaluated system was installed or tested end to end.

**The closest matches solve different parts of the workbench.**

The central distinction is between preserving a conversation, displaying its files, and maintaining a reviewed body of work. A session viewer preserves discussion. An artifact viewer presents HTML, a chart or a slide deck. A workbench additionally explains which question the output answers, what decision was accepted, which evidence supports it, and whether changed inputs have made it stale. This is the comparison framework used below, rather than treating every product labeled “dashboard” as equivalent.

| Candidate | Documented capabilities | Best comparison with SPACE | What remains unverified or custom |
|---|---|---|---|
| **[AionUi](https://github.com/iOfficeAI/AionUi)** | Claude Code/Codex integration, cowork workspace, task board, file-change tracking, PDF/Office/PPT/HTML/Markdown previews | Sessions plus project files and visible deliverables | Import of independently created historical transcripts; governed question/decision records |
| **[CloudCLI](https://github.com/siteboon/claudecodeui)** | Claude/Codex sessions, file explorer, editing, Git and extensible tabs | Browser workbench around existing coding agents | Domain-specific questions, decisions, drawings and artifact publication need extensions |
| **[Open WebUI + Open Terminal](https://docs.openwebui.com/features/open-terminal/coding-agents/)** | Claude Code/Codex execution, filesystem workspace, live previews, chat artifacts and persistent notes | Broad integrated web workspace | Historical transcript ingestion and evidence-linked decision lifecycle were not established |
| **[marimo + Studio](https://marimo-team.github.io/marimo-studio/)** | Reactive analysis; paired coding agents; dashboard/report/slide views backed by computed outputs | Data → analysis → several presentations of the same result | Cross-session question/decision governance; Studio is experimental |
| **[LibreChat](https://www.librechat.ai/docs/features/artifacts)** | Editable HTML/React/SVG/Markdown/Mermaid artifacts and generated-file previews | Chat-side artifact creation and inspection | Existing Claude/Codex history import and SPACE-style work semantics |
| **[AFFiNE](https://github.com/toeverything/AFFiNE)** | Documents, canvas, linked pages, databases, shapes and slides | Persistent visual knowledge workspace | Session import, evidence extraction and review transitions require integration |

**AionUi is the first product I would inspect for the overall user experience.** Its file previews cover much of the user’s requested output range, and its WebUI can run as a headless server. That makes it a more direct comparison than a general personal-assistant clone. CloudCLI is the stronger extension reference: its official plugin starter adds a project-statistics tab, receives project/session context, and can use a backend through RPC. Its API does not expose unrestricted interaction with the built-in chat, and frontend plugins are not runtime-sandboxed. Those boundaries matter when considering it as a product foundation. ([AionUi WebUI guide](https://github.com/iOfficeAI/AionUi/wiki/WebUI-Configuration-Guide), [CloudCLI plugin starter](https://github.com/cloudcli-ai/cloudcli-plugin-starter))

**marimo is the closest data-to-results precedent.** `marimo pair` explicitly supports Claude Code and Codex working with a live notebook that the human can also inspect and edit. Studio then places notebook outputs into separate dashboard, report, presentation or paper views, with links back to the computing cells. This supplies computational provenance; it does not automatically reconstruct the human reasoning and accepted decisions in old chat sessions. Core marimo is established relative to the small, explicitly experimental Studio project. ([Agent pairing](https://docs.marimo.io/guides/generate_with_ai/marimo_pair/), [Studio](https://marimo-team.github.io/marimo-studio/))

Popularity provides context, not a selection rule. Approximate GitHub stars observed during this review were Open WebUI 158k, AFFiNE 74.4k, LibreChat 47k, AionUi 34.2k, marimo 23.5k and CloudCLI 14.6k; Studio had about 71. These are rounded repository snapshots, not active-user counts. Licensing also differs: AionUi and marimo use Apache-2.0, LibreChat uses MIT, and CloudCLI uses AGPL-3.0. Current Open WebUI has a custom license with branding conditions; AFFiNE combines MIT code with separately licensed backend/enterprise portions. A product fork must evaluate the specific edition and files used. ([Open WebUI license](https://docs.openwebui.com/license/), [AFFiNE licensing](https://github.com/toeverything/AFFiNE/blob/canary/packages/backend/server/LICENSE), [LibreChat](https://github.com/LibreChat-AI/LibreChat), [AionUi](https://github.com/iOfficeAI/AionUi), [marimo](https://github.com/marimo-team/marimo), [CloudCLI](https://github.com/siteboon/claudecodeui))

**Claude’s current products confirm the session-to-website model.**

The user’s premise is correct: current Claude Code documentation describes turning session context, repository files and connected information into an interactive page hosted on Claude. Revisions retain the same URL; another session can continue work by attaching the artifact or receiving its URL. These are persistent outputs with update behavior, rather than a temporary preview of an HTML file. Current documentation supersedes the narrower restrictions in the original launch announcement. ([Claude Code artifacts](https://code.claude.com/docs/en/artifacts))

There are important boundaries. A Code artifact is one self-contained page, without an application backend or multiple routes. Publishing requires a Claude account login rather than API-key/cloud-provider credentials. Private, organization and public sharing depend on policy. Live connector access uses the viewer’s Claude connections; a published page cannot directly call the author’s local MCP servers. Current documentation also excludes organizations with HIPAA, CMEK or ZDR configurations enabled, which is material to the separately discussed patient-data product. ([Current artifact requirements](https://code.claude.com/docs/en/artifacts))

**Claude Data and Code artifacts should be compared separately.** Anthropic’s November 10 announcement identifies Data as the current name for Dashboards and announces its general availability, alongside Whiteboards and Sheets beta. Data connects to organizational systems and supports refresh/caching and tracked edits; certified queries and live sharing remain beta. This is a connected-data product, not documented as an automatic importer of arbitrary local Claude/Codex history. Whiteboards and Sheets add editable collaborative surfaces. ([Product announcement](https://claude.com/resources/articles/sheets-whiteboards-data))

For SPACE, the transferable product contract is: a result has an identity, sources, a revision, an owner, an access policy and a way to update. A data dashboard additionally has a query or snapshot and freshness state. An editable drawing has its source document as well as a rendered preview. These contracts can be implemented over SPACE’s files and web host without reproducing Claude’s entire hosted platform.

**DSH already offers partial equivalents through plugins.**

The repository’s own README names **DeepSeek Harness (`dsh`)**, making this the strongest identification of the user’s acronym. The exact intended plugin remains unconfirmed. DeepSeek Harness has a web UI and plugin architecture; its official repository is MIT licensed and labels the project developer preview. Its large core audience should not be treated as maturity evidence for every community extension. ([Local README](../README.md), [DSH core](https://github.com/deepseek-ai/deepseek-harness))

| DSH component | What the reviewed implementation provides | Relevance and limit |
|---|---|---|
| **[Better Sidebar](https://github.com/omdsh-dev/DSH-better-sidebar)** | File manager/editor, Markdown/Mermaid, sandboxed HTML, JSONL cards, Git, terminals and extensible sidebar pages | Closest DSH workbench shell; no full question/decision/evidence registry established |
| **[Abid’s dsh-visualizer](https://github.com/abiddotdev/dsh-visualizer)** | Streaming HTML previews, downloads, comments, explicit export/share, gallery and persisted widget state | Closest artifact-publication plugin; small community project |
| **[Moses14159’s dsh-visualizer](https://github.com/Moses14159/dsh-visualizer)** | Structured ECharts specifications and SVG/HTML widgets using session/tool events | Separate implementation; do not assume Abid’s gallery/export features exist here |
| **[Session Insights](https://github.com/GreenLv/dsh-session-insights)** | Offline HTML and JSON retrospectives from session history | Describes workflow activity, failures and completion evidence; not a scientific-results dashboard |

Abid’s plugin provides an especially useful design precedent: generated HTML remains associated with a durable tool call, and explicit export retrieves that successful call from the log. Export is not automatic. Its content-based URLs and capability-key sharing differ from a stable document ID with per-user authorization; default retention is 30 days unless pinned. These details make it a useful implementation reference while showing why “has artifacts” does not imply the same publication contract as SPACE needs. ([Plugin documentation](https://github.com/abiddotdev/dsh-visualizer), [host implementation](https://raw.githubusercontent.com/abiddotdev/dsh-visualizer/master/src/index.ts))

The adoption difference is substantial: Better Sidebar had about 5.1k stars, while the two visualizers and Session Insights had approximately 14, 7 and 2 respectively. These figures do not prove quality or lack of quality, but they argue for a compatibility test before adopting a plugin as infrastructure. The two identically named visualizers are distinct implementations. No inspected DSH source established a complete native importer for both historical Claude and Codex sessions plus a reviewed question → decision → evidence → artifact graph. That is a boundary of this review, not proof that no extension could provide it. ([Better Sidebar](https://github.com/omdsh-dev/DSH-better-sidebar), [Abid visualizer](https://github.com/abiddotdev/dsh-visualizer), [Moses visualizer](https://github.com/Moses14159/dsh-visualizer), [Session Insights](https://github.com/GreenLv/dsh-session-insights))

**The broader landscape offers reusable components rather than one complete substitute.**

For historical-session capture, **SpecStory** is particularly relevant: its CLI launches Claude or Codex, stores local Markdown history, and can export past sessions through `sync`. Optional cloud search/sharing is a separate service. **claude-code-transcripts** turns local Claude JSONL into paginated HTML and a prompt/commit timeline, but currently documents broken web-session export commands. A small project, **threadle**, maps existing Claude/Codex sessions and tool/file relationships; its three observed stars and warnings about changing provider formats make it an architectural reference rather than a mature dependency. ([SpecStory quickstart](https://docs.specstory.com/quickstart), [transcript exporter](https://github.com/simonw/claude-code-transcripts), [threadle readers](https://docs.threadle.sh/sessions/overview/))

For publication, **Quarto** turns agent-authored Markdown/notebooks into websites, dashboards, reports and slides. **Observable Framework** and **Evidence** are more focused data-app/report engines. **Excalidraw** preserves editable drawings alongside SVG/PNG outputs, while **Slidev** provides file-authored presentations. These are possible renderer components; they do not supply SPACE’s work ownership or decision governance. Reuse a renderer only where an existing SPACE surface lacks the required capability. ([Quarto](https://quarto.org/docs/guide/), [Observable Framework](https://observablehq.github.io/framework/), [Evidence](https://github.com/evidence-dev/evidence), [Excalidraw](https://github.com/excalidraw/excalidraw), [Slidev](https://github.com/slidevjs/slidev))

Other reviewed tools cover adjacent needs. Happy, HAPI and Opcode focus largely on session access, control and project navigation. AnythingLLM helps query documents; SiYuan provides linked, persistent knowledge. These are useful comparisons but do not establish the complete requested workflow. Vibe Kanban remains a planning/review reference, but its company announced shutdown and retirement of hosted services in April 2026; the local/community project should be assessed separately. ([Happy](https://happy.engineering/), [HAPI](https://github.com/tiann/hapi), [Opcode](https://github.com/winfunc/opcode), [AnythingLLM](https://github.com/Mintplex-Labs/anything-llm), [SiYuan](https://github.com/siyuan-note/siyuan), [Vibe Kanban announcement](https://www.vibekanban.com/blog/shutdown))

**SPACE should add a shared results contract to the surfaces it already has.**

A bounded source inspection found existing session listing/log/keep routes, associated transcript/digest preservation, Studio views for slides/drawings/mind maps/Work/Delivery, and Page Delivery views for Preview/Artifacts/Checks. These are substantial parts of the requested product. Code presence is not a running-browser acceptance test, and a general Codex adapter was not confirmed in the inspected session module. The next implementation should extend these paths after checking their current contracts. ([Session code](../plugins/haipipe-toolkit/servers/workbench/chat.py), [Studio renderer](../plugins/haipipe-toolkit/servers/workbench/studio_tabs.py), [Delivery renderer](../plugins/haipipe-toolkit/servers/workbench/workbench-task-draft/space_views.py))

The proposed flow is **selected sessions + project files → extracted candidates → reviewed work records → registered artifacts → existing workbench views → deliberate publication**. Canonical questions, decisions, Studio topics, Pages and Run receipts retain their current homes. A derived, rebuildable index links them; it should not create a competing decision ledger.

| Proposed addition | Minimum behavior | Why it matters |
|---|---|---|
| **Session adapters** | Normalize provider, session/event identifiers, timestamp, scope and source revision; preserve the original record or secure reference | Supports Claude/Codex/DSH without losing exact evidence |
| **Candidate extraction** | Propose questions, decisions, actions and outputs; record supporting turns/files | Separates an agent’s inference from an accepted decision |
| **Result registration** | Stable ID, type, owner, canonical file, renderer, source session/run, revision, inputs and review state | Gives every dashboard, drawing or deck a durable identity |
| **Dependency tracking** | Store code/data versions or hashes; mark affected results stale after input changes | Makes refresh and reproducibility explicit |
| **Existing-view integration** | Render registered results in Studio, Delivery and family workbenches; navigate back to evidence | Preserves the established work model |
| **Publication** | Share a chosen revision or latest accepted output with explicit access scope | Keeps private source conversations separate from delivered work |

A decision needs its rationale, source, acceptance evidence and supersession relationship. An artifact needs its editable source as well as its preview. A dashboard needs to distinguish a frozen snapshot from live data and record the last successful refresh. Reimporting a session should update an identified source, not duplicate all its questions. Executable HTML should render inside an appropriate isolated boundary rather than receiving the workbench’s own origin privileges. These are proposed requirements, not claims about implemented SPACE behavior.

The first demonstration should use **one Claude session and one Codex session concerning the same question**, with their existing project files. Show a question tracker, accepted decision, data dashboard, drawing and slide deck through the current website. A reviewer must be able to trace one displayed number and one decision back to exact sources. Reimport must be idempotent; a changed dataset must mark its dashboard stale; a revised decision must retain its predecessor; sharing the result must not expose the raw transcript. This tests the missing integration directly before adding more themes or replacing infrastructure.

The recommended inspection order is **AionUi for output navigation, CloudCLI’s plugin starter for context-aware extensions, SpecStory for history preservation, and marimo pair/Studio for reproducible multi-format results**. Claude artifacts and DSH’s visualizers supply publication patterns. The enduring product value for SPACE is the explicit relationship between the question, collaboration, accepted decision, execution and delivered evidence—and keeping that relationship intact when the agent, file or presentation changes.
