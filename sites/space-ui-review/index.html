深色模式也要读得清

目标条使用固定浅底色，文字却跟随深色主题变浅。

指定颜色计算：原标题 1.10:1，原说明 2.36:1；建议配色 9.94:1 / 4.65:1。非浏览器实测。

依据、改法与理由

共享样式的深色正文为 #e8e8e6、次要文字为 #a0a09c；目标条背景固定为 #eef3fb。目标标题继承正文色，末尾说明使用 --muted。

实际影响

建议怎么改
让目标条背景使用语义令牌 --soft，并成对检查正文、次要文字。保留原有主题切换机制。
为什么这样改
克制不等于低可读性。颜色应表达层级，并在亮暗两种环境中保持足够对比。普通小字号文字以 4.5:1 为验收基线。
如何验收
在 Design 的 Goals × methods 中切换亮／暗主题，读取 computed style，检查两类文字；同时检查 held 卡片等固定浅底样式。

这是颜色组合的条件性风险，不是整站无障碍合规结论。

菜单展开，点击范围不应缩小

触屏导航的 44px 高度被展开状态的规则覆盖。

依据、改法与理由

coarse pointer 规则设 height:44px；更具体的 .focus-rail.is-open a 后设 height:auto、min-height:28px、上下 padding 各 5px。单行 line-height 为 20px，推算展开后约 30px。

实际影响
宽度大于 600px 的触屏设备仍显示侧栏；展开后的单行链接比折叠时更难点。手机窄屏走另一套导航，不能据此判定同样受影响。
建议怎么改
在 coarse pointer 条件内，为展开链接补 min-height:44px；多行仍允许增高，桌面布局保持原密度。
为什么这样改
视觉边界可以轻，实际触控范围应宽裕。控件展开后应保持交互尺寸的一致性。
如何验收
768px 触屏条件下检查左右侧栏的单行、多行链接高度和相邻点击；再检查桌面指针。

约 30px 是代码推算，尚未实测。WCAG 2.2 最小目标要求为 24px 且有例外；这里不能据此宣称违反 WCAG，44px 是本项目已有的触屏目标。

让弹窗标题同时成为它的名称

可见标题存在，但 dialog 没有引用它。

依据、改法与理由

生成的 dialog 没有 aria-labelledby 或 aria-label；脚本把标题写入 data-viewer-title。iframe 的 title 只命名 iframe。

实际影响
辅助技术进入弹窗时，可能无法从弹窗名称识别当前预览内容，尽管视觉上已有标题。
建议怎么改
给现有标题 span 一个稳定 id，并由 dialog 的 aria-labelledby 引用；继续使用现有动态标题。
为什么这样改
同一个标签同时服务视觉与辅助技术，无需增加一行可见说明。语义精度也是 UI 精度。
如何验收
打开两个不同预览，检查无障碍树中的 dialog name 随标题变化；检查 Escape、关闭按钮及返回原触发链接。

已确认标记缺少名称关联；尚未用读屏软件测试实际播报。

跳到哪里，键盘操作也到哪里

Go 展开并滚动到目标，但没有显式转移焦点。

依据、改法与理由

Go 的处理器关闭 popover、展开折叠内容、scrollIntoView 并闪亮目标，没有目标 focus()；同文件的预览关闭逻辑则明确恢复焦点。

实际影响
画面已经定位到任务，下一次 Tab 却可能从托盘入口附近继续，视觉位置和操作位置脱节。具体回退行为依浏览器而定。
建议怎么改
展开后把焦点交给目标中的合适控件；若目标是静态区域，可临时使用 tabindex=-1 和 focus({preventScroll:true})，保留自然 Tab 顺序与减少动画设置。
为什么这样改
视觉注意力与操作焦点应到达同一目的地。滚动和高亮不能替代键盘定位。
如何验收
仅用键盘打开托盘、Go、Tab；测试嵌套折叠、非按钮目标和 reduced-motion。先确认问题，再选定焦点落点。

缺少显式焦点转移是代码事实；实际键盘路径仍待浏览器验证。

空结果不必占一个章节

无结果时，模板主动生成 “Nothing here yet.” 章节。

依据、改法与理由

result() 为空时传入非空占位段落；_section 仅在 body 为空时跳过，因此该调用会生成章节。根规则要求隐藏没有内容的章节。

实际影响
模板生成一个没有结果可读的标题和正文，增加扫描距离。最终路由页面是否有其他处理仍待实测。
建议怎么改
无结果时不生成这一结果章节；单独保留流程中的真实动作、缺输入原因和失败提示。
为什么这样改
每个可见章节都应承载内容或行动。省略空壳让有效内容更容易被找到。
如何验收
检查尚无结果、首次产生结果、运行失败三种场景；空结果消失时，下一步或错误原因仍可见。

已确认模板输出与规则冲突，不代表所有最终页面都出现了这个占位。

依据、改法与理由

如何验收

先让指导文件说同一件事

根规则已经更新，部分 UI 指南仍要求状态词、进度数和空章节。

依据、改法与理由

指南要求 “Every mark has a word”、进度 tally、关闭栏的 state word、空 Interaction 的占位；根规则要求标记、禁止进度 tally 并隐藏空章节。word_span 已跟随新规则。

实际影响
不同 agent 读取不同文件会产出相互冲突的页面；旧表达可能在后续生成中重新出现，导致重复维护。
建议怎么改
以根规则为准修订活动指南，历史决策转入历史记录；同步复查 focus-assets/README 的展开规则。可见状态文案与辅助技术名称应分开处理。
为什么这样改
一致性首先来自统一的执行依据。精度需要可重复的规则，而不是每次依靠个人判断。
如何验收
让新的审阅上下文仅根据更新后的指南生成一个示例章节，检查标记、等待动作、空章节和读屏名称。
