QD4 Generate the lexicon instead of hard-coding it

🧭 Opening

The engine's first step estimates how common a construct is in the corpus by reading a keyword list, so how does that list get generated from the construct definition instead of being written into the code by hand?

Boundary

✅ Covered here Deriving the keyword list from the construct definition and computing the base rate from it, with no hand-written word left anywhere in the run.

↪ Covered elsewhere Turning a sentence into a vector is QD1, hunting the hard cases that grow the sample from 60 to 140 is QB1, and the standard that picks which construct to label at all is QC3.

Why this matters

That first estimate is the base rate, and the keyword list it reads today is the one hand-written for openness, so pointing the engine at any other construct means editing code.

It is the last hard-coded piece behind the claim that this is a general engine, and for as long as it stands the claim is not true.

The list also sits at step 0 of the pipeline, before QD1 turns a sentence into a vector, which makes it the first thing a new construct meets and the first place a new construct fails.

lib/sample.py is already written and needs a base rate before it can draw a representative sample, so the generation of that list is the piece not yet connected.

🎯 Items to Finish0/3
☐
🧪A construct with nothing to do with physicians produces a lexicon in one run

Point the engine at a construct unrelated to physicians, sarcasm for example, and a single run produces the keyword list with nobody writing it.

The test construct is picked far from the corpus this project started on for a reason: a list that works only because someone already knew the openness vocabulary proves nothing about the mechanism. Sarcasm shares none of that vocabulary, so if the generation step still produces a usable list, the list is coming from the construct definition rather than from the person who wrote the code. This is what ZD's note-update-v3 Part 8 asks for when it says the openness-specific hard-coded assets should become mechanisms.

☐
📊The base rate is computed from that generated list with nothing hard-coded in the path

The generated list is used to estimate the base rate, and no line anywhere in that run is written for one particular construct.

Producing a list is only half the finish line, because it still has to survive being used. The base rate is what lib/sample.py needs before it can draw a representative sample, so the run has to go from a construct definition to a lexicon to a base rate with nobody stepping in halfway. The one number available for comparison is openness at roughly 6.6%, which was measured with the hand-written list.

☐
📌The result is written under this line

Whatever the run produces, the generated list and the base rate it yields, is posted here on this face.

This face carries its own evidence instead of pointing at a run somewhere else, so whoever runs it writes the list and the number down here. Until that lands, a reader cannot tell whether the generation step was tried and failed or was never run at all.

📍 Where we are

The lexicon in probe_base_rate.py is hard-coded, written by hand for openness.

lib/sample.py is already written and is waiting for a list to be fed to it.

ZD's note-update-v3 Part 12 files the LLM construct→probe lexicon generation under what is not yet done, which there means real runs rather than engine code: the engine code exists and this one step has not been connected to it.

📖 Glossary

base rate: how common the construct is in the corpus, measured at roughly 6.6% for openness, and something a representative sample has to know first or it comes out skewed.

lexicon: a keyword list, used for a rough estimate of the base rate.

construct→probe generator: ZD's name for the step that derives a probe lexicon from construct.definition, replacing the hand-written list.
