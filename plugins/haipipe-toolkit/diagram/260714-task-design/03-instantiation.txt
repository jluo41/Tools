THREE MECHANISMS
================

  The instance is glued to the pattern by exactly three things. Nothing else.


① SCHEMA POINTER — single source of truth
=========================================

```text
   fn/stage-plan.md:8      "Schema source of truth: .../plan-schema.md"
   fn/stage-report.md:8    "Schema source of truth: .../plan-schema.md (Report section)"
   ⇒ the instance READS the schema; it never RESTATES it as authoritative.
```

  🔑 This is the strong part of the design. plan-schema.md has ONE writer
     (haipipe-workflow) and three readers. Change the shape once, all instances
     inherit it. Textbook single-sourcing.


② NAMING — task's own STAGE vocabulary, not the workflow verb name
==================================================================

```text
   haipipe-workflow  plan      report      (+ build execute inspect template)
   haipipe-task/fn/  stage-plan  stage-report   audit
   ⇒ the `stage-` prefix names task's OWN "Four Stages" (SKILL.md), it does NOT
     borrow the workflow verb's name.
```

  🔁 RENAMED 2026-07-14 (JL): the files were `workflow-{plan,report,audit}.md`. The
     `workflow-` prefix collided with the haipipe-workflow SKILL and overloaded the
     word 5 ways (R1). Dropped in favour of task's own Stage vocabulary. Closes R2
     (audit was mis-prefixed — it instances NO workflow verb, so it takes a bare
     `audit.md`, mirroring nothing). See 05 · R7.


③ TEMPLATE → SPECIFIC — the fill-in-the-blanks
==============================================

```text
   TEMPLATE (haipipe-workflow)         SPECIFIC (haipipe-task)
   ────────────────────────────        ──────────────────────────────────
   Phase: "Author"                     Phase: "Run" / "Gate1" / "Gate2"
   Step:  "write script"               Step:  "gate1:code-review"
   agentType: <generic>                agentType: haipipe-task-reviewer-agent
   plan.yaml                           workflow/plan.yaml + plan-script-<name>.yaml
   ⇒ the instance adds a SECOND layer (task plan + per-script plan) the template
     does not have, and pins the Run/Gate1/Gate2 phase convention.
```


THE LIFECYCLE, AS ADVERTISED vs AS RUN
======================================

```text
   ADVERTISED (haipipe-workflow SKILL.md + concepts.md):
     plan.yaml ──build──▶ .workflow.js ──execute──▶ results ──report──▶ report.yaml
      (human)             (machine, GENERATED)      (raw)               (structured)

   AS RUN for task:
     plan.yaml   ← observability record (intent), written by stage-plan
     .workflow.js ← HAND-SHIPPED (ref/task-lifecycle.workflow.js), not built
     results/    ← produced by runs/<run>.sh (papermill), not by `execute` verb
     report.yaml ← written by stage-report (evidence), mirrors plan

   ⇒ `build` and `execute` (the two MIDDLE acts) are effectively bypassed for task.
     The pattern's four acts survive as VOCABULARY; only Plan and Report are live
     verbs in the task instance. This is not wrong — but it is undocumented.
```
