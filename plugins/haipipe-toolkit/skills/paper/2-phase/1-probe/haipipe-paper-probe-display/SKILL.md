Skill: haipipe-paper-probe-display
=========================================

display probe worker for `haipipe-paper-section-edit`.
Owns the display lifecycle for one section: identifying what figures/tables the section needs, planning which display units serve which claims, requesting missing units via DR rows in the 4-display inbox (section-edit never creates displays), and linking existing/done units back to the section.

```
/haipipe-paper-probe-display                       → status dashboard
/haipipe-paper-probe-display audit <section>       → Phase 1: what displays needed?
/haipipe-paper-probe-display plan <section>        → Phase 2: map claims to units; missing unit → DR row
/haipipe-paper-probe-display link <section>        → Phase 3: harvest — connect landed units to section
/haipipe-paper-probe-display review <section>      → Phase 4: pre-submission display check
```

## Hard Boundaries

1. **NEVER create ad-hoc plots inline.** All figures and tables route through display units in `0-displays/` and are generated by task-folders.
   The paper layer plans, it does not plot.

2. **Section-edit never CREATES a display** (JL 2026-07-10: "we don't create the display ourself").
   A unit that does not exist is REQUESTED: append a DR row to `0-lifecycle/4-display/_DISPLAY_REQUEST.md` (the display stage's inbox) and mark the need 📨 requested in `_DISPLAY_{section}.md`.
   The display stage — with its index, unit interrogation, venue display set, gallery, and CHECKLIST — is the ONLY creator of units.
   No `/haipipe-task` calls, no PP-card commissioning of unit generation from section context.
   SCOPE: this ban binds section/narrative context.
   When THIS worker is invoked BY the display stage (4-display) on its own accepted units, commissioning is that stage's job and follows the display hub's PROBE lanes — no DR row is filed into the stage's own inbox.

3. **NEVER fabricate display content.** Display units contain real data outputs.
   The agent plans layout and routing, not data.

4. **`_DISPLAY_{stage}.md` is the working document.** It records what displays are NEEDED (need → unit → status), parallel to `_CITATION_` and `_VALUES_`.
   The units themselves live in `0-displays/displayNN/` with their own `float.tex`, rendered output, and source data; the agent links units back to needs, not the other way.

5. **the user's display comments go into `0-lifecycle/4-display/4-display.md`** as `> USER:` threads (the display stage's md-first working brain; 4-display.tex is GENERATED by sync and never hand-edited), NOT into per-unit `float.tex`.


## Four Phases (fully automatic; direct-ROUTE is RETIRED — JL 2026-07-07 harvester ruling)

```
Phase 1: AUDIT        what displays does this section need?
Phase 2: PLAN         which display unit serves which claim/beat; sweep
                      0-displays/ + the display index for an EXISTING unit
                      first (paper-local sweep). A unit that does not exist
                      becomes a DR request row in the 4-display inbox — this
                      worker NEVER commissions generation (no /haipipe-task and
                      no probe dispatch; RETIRED JL 2026-07-10).
Phase 3: LINK         harvest — follow the probe section's displays: lane; connect
                      landed 0-displays/ units back to needs + section tex
Phase 4: REVIEW       pre-submission display check (content matches claims)
```

All phases run automatically without stopping for human input.
Human review of generated displays happens ONLY in the CHECK phase (haipipe-paper-check).
During CHECK, the human reviews displays, adds `> USER:` comments, and decides.
If CHECK restarts PROBE, the agent reads those `> USER:` comments and re-plans.


## Phase 1: AUDIT

Read the section outline and narrative.
For each paragraph, identify:

- Does this paragraph make a claim that needs visual support?
- Is there a `\ref{fig:...}` or `\ref{tab:...}` already in the tex?
- Does the _CITATION_ or _VALUES_ map reference a display?

Output: a gap list showing which paragraphs need displays and which already have them.

```
P#  | Claim/beat | Display needed? | Current display | Status
P1  | variation  | no              | --              | --
P4  | results    | yes (table)     | display03       | ✅ linked
P5  | gradient   | yes (figure)    | --              | 🔍 needed
```


## Phase 2: PLAN

For each needed display, plan:

- **What type**: figure (plot), table, diagram, illustration
- **What it shows**: which claim/beat it supports
- **Which display unit**: existing `0-displays/displayNN/` or new unit needed
- **Data source**: which task-folder output feeds it

Write the plan to `_DISPLAY_N-section.md` (or update the narrative's `_DISPLAY_` file if it exists at the paper level).

**Missing unit -> DR request.** Append to `0-lifecycle/4-display/_DISPLAY_REQUEST.md` (create the file on first request; bullet lines, no tables; DRNN numbering per file):

```markdown
## DR03 -- <short title>                        status: requested
- from: 5-section-edit/4-llmtrait · P4 · 2026-07-10
- claim: <the exact claim the display must support>
- form: figure | table | diagram | illustration   (suggestion; the display stage decides)
- evidence: <source hint: tasks/ path · metrics.json · _VALUES_ entry>
- unit: --                                        (display stage fills: 0-displays/displayNN-slug/)
```

Status flow (only the display stage advances it): `requested -> accepted -> done (unit: <path>)` or `declined (<reason>)`.
Mark the need `📨 requested (DRNN)` in `_DISPLAY_{section}.md` and move on — never block on the request.


## Phase 3: LINK (harvest, automatic)

The agent links generated display outputs to the section tex without waiting for human approval.
The human reviews the linked displays during CHECK.

0. LINK only units that EXIST (or whose DR row is `done` with the unit path filled).
   A `requested`/`accepted` DR row stays 📨 pending — flag it for CHECK, never pre-place a `\ref` for it.
1. Ensure the display unit's `float.tex` is correct
2. Add `\input{0-displays/displayNN/float.tex}` to the section tex if not already present
3. Add/update `\ref{fig:...}` or `\ref{tab:...}` in the prose
4. Sync outline with display references
5. Backfill to `0-lifecycle/4-display/` if needed

If a task-folder has not produced output yet (still running or failed), the agent flags that display as pending and continues.
Pending displays are reported in CHECK.


## Phase 4: REVIEW (pre-submission)

For each display referenced in the section:

1. Does the display content match the claim it supports?
2. Do the numbers in the display match _VALUES_?
3. Is the caption accurate?
4. Does the `\ref` in the prose point to the right display?
5. Is the display rendering clean in the compiled PDF?

## Done criteria

- [ ] All display needs identified
- [ ] All displays planned and mapped to units
- [ ] All missing units filed as DR requests in the 4-display inbox (📨 pending flagged for CHECK)
- [ ] All available display outputs linked in section tex
- [ ] Pending/failed displays flagged for CHECK (not blocking)
- [ ] _LOG updated with display probe summary


## Anti-patterns

- ❌ Creating ad-hoc matplotlib plots inline
- ❌ Commissioning display generation from section-edit (a direct /haipipe-task, or a probe section dispatched at a task) — file a DR request; only the display stage creates units
- ❌ Editing display content directly instead of re-running the task
- ❌ Placing `\ref{fig:...}` for a display that hasn't been generated yet
- ❌ Putting the user's comments into per-unit float.tex or the generated 4-display.tex (they go in 4-display.md as > USER: threads)
