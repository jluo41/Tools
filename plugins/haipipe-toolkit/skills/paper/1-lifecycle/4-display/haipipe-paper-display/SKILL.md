Skill: haipipe-paper-display
======================================

Stage orchestrator for the **display** stage (stage 4, venue-ALIGNED). The user invokes this skill; it drives the phases internally.

It answers one question:

```text
What evidence artifacts does the reader need to see, and are they ready?
```

Display items are figures, tables, diagrams, and other manuscript-visible objects that carry evidence and story. A display item is not just a file. It has a job:

```
What claim does this display support?
Where does the evidence come from?
What should the reader learn in five seconds?
Where does it appear in the paper?
Is it ready to input into the manuscript?
```

Read first: `../../../PHILOSOPHY.md`, `../../../wiki/04-lifecycle-map.md`.

**Done-gate: `CHECKLIST.md`** (this skill's folder) is the canonical, scannable done-gate for this stage and the home of the gallery requirements. The paper's stage files point here instead of restating them. Walk it before asking for the stage gate.

## Artifact Spec

**The stage doc is an md → tex → pdf trio**, like every other stage (0-seed.md, 3-narrative.md ... the md is the working doc; here the md additionally GENERATES a compilable gallery):

```text
0-lifecycle/4-display/
├── 4-display.md          THE BRAIN — working doc; the ONLY file humans and phases edit
├── 4-display.tex         GENERATED gallery — rebuilt by sync from the md; NEVER hand-edited
├── 4-display.pdf         compiled gallery (compile from the paper root via ./1-compile.sh)
├── _LOG_4-display.md     phase progress journal (create on FIRST invocation; missing = defect)
└── _DISPLAY_REQUEST.md   request INBOX: sections file DR rows for units they need but must
                          not create (JL 2026-07-10); this stage consumes them

0-displays/               THE REAL ASSETS — per-unit folders:
└── displayNN-<slug>/
    ├── README.md         unit-local record (claim/kind/source/caption-job/fragility/status)
    ├── float.tex         caption + \label + asset reference; the block the gallery \inputs
    ├── preview.tex/pdf   standalone per-unit review artifact
    ├── assets/           the WINNING rendered asset (figure.pdf / table-body.tex)
    ├── candidates/       PROBE-produced candidate renders (methods A/B/C...), pre-decision
    ├── source/           rebuild spec + provenance (script/spec/prompt + data refs)
    └── versions/         superseded variants + demoted candidates, kept for history
```

**Retired files** (absorbed into `4-display.md` — migrate at stage entry, see DRAFT step 0): `4-display-probes.md` (the old planning brain), `4-display-preview.txt` (the old ASCII contact sheet), and `%% {USER}:` comments inside `4-display.tex` (the old comment home). One brain, one file.

**Content structure of `4-display.md`** (canonical template: **`ref/display-template.md`** — the same stage-template convention as seed/claims/pitch/narrative):

- **Venue Set** — the venue's standard display set + limits from `2-venue.md` (principle 9); plus the **gallery config** block (sizing knobs sync emits into the generated tex preamble).
- **Display Map** — one record line per display; row order = narrative order = gallery order.
- **Probes** — the phase plan, shaped like the seed/claims `Probes` section: each probe is a `###` sub-item `<ID> -- <title> -- <status>` with `Lane:` / `Route:` / `Serves:` / `Gated on:` / `Outcome:` field lines (evidence entries also carry the family's `Detail: 1-probes/PPNN_<slug>.md` pointer), separated by `---`. IDs number within lane: `S` sweep, `E` evidence, `R` render. Status is `▶ ready`, `✋ gated` (on a named display-subsection thread), or `done` (Outcome written in). DRAFT proposes; the user strikes entries at the gate; PROBE executes only what survives and writes each Outcome back.
- **Paper-section groups** — one `-----` section per PAPER SECTION, in narrative order, opening with a `venue expects:` line (that section's display units from the 2-venue.md blueprint, so a mandated-but-missing unit is a visible GAP in place); **each display is a `###` subsection** inside its group: claim/status line, takeaway, evidence source, **lettered method-candidate lines** (the try-different-methods surface), ASCII sketch (real numbers when known), caption job, fragility, `> USER:` / `> CC:` threads. Group membership mirrors the map's `section` column (mismatch = defect); the md grouping mirrors the generated gallery's `\section*`/`\subsection*` structure one-to-one.
- **Parking** — kept-but-unused displays; listed here, never `\input` into the manuscript.

**Formatting (4-display.md):** `=====` for the title; `-----` for sections — the fixed sections (Venue Set, Display Map, Probes, Parking) AND one group per paper section; each display is a `###` subsection inside its paper-section group, and each probe a `###` sub-item inside `Probes` (`###` is the ONLY `#`-style level used). One sentence per line (semantic line breaks); ASCII sketches in fenced blocks. **NEVER markdown pipe tables** (JL 2026-07-10): anywhere a table suggests itself, write record lines instead — `- E2 ✋ <action>` with indented `route:` / `serves:` / `gated on:` / `outcome:` fields; `- A <form> via <route> -> <output> · verdict: ...`. Pipe tables fight hand-editing, semantic line breaks, and diff review. Aligned plain text INSIDE a fenced sketch is fine — it sketches a LaTeX table, it is not doc structure.

**Sync (md → tex), owned by REVISE:** rebuild `4-display.tex` wholesale from the md —

1. Preamble + the gallery config knobs from the md (width cap, float pinning, compact spacing). Gallery sizing lives HERE, never in a unit's `float.tex` (units keep native full size for manuscript use).
2. Walk the md's paper-section groups in order (membership mirrors the Display Map's `section` column — fix any mismatch in the md first): each `-----` group emits its `\section*{<paper section>}` banner, then each `###` display subsection emits `\subsection*{Figure N. <name>}` / `Table N. <name>`, the display's small-font interrogation verdict (from its md block), and `\input{0-displays/<unit>/float.tex}`.
3. Emit the Parking section last.
4. Recompile `4-display.pdf` from the paper root. A stale pdf or a hand-edited tex is a defect: fix the md, re-sync, recompile.

**Status vocabulary:** `planned` → `data-ready` → `candidates` → `rendered` → `input-ready` → `inserted` → `reviewed`. The md map is canonical; REVISE mirrors status down into each unit's `README.md`.

**Done-criteria:**
- [ ] `4-display.md` present; Display Map consistent with units on disk (no orphans either way)
- [ ] Every current display block has claim, takeaway, evidence source, status
- [ ] No block stuck at `candidates`: a winner is promoted (decision recorded in the block) or the block is parked
- [ ] `4-display.tex` regenerated from the md; `4-display.pdf` compiles from paper root and is current
- [ ] All displays referenced in narrative (`3-narrative.md`); `_DISPLAY_REQUEST.md` rows advanced (no row left `requested`)
- [ ] All `> USER:` threads addressed (`> CC:` reply) or resolved by the user
- [ ] `Probes` entries all terminal: `done` with an `Outcome:` filled, or skipped by the user (logged); no `✋` entry silently dropped or run while its gating thread was unruled
- [ ] CHECKLIST.md walked and all items pass

/haipipe-paper display <paper-dir> draft      -> run/redo DRAFT  -> STOP for user review

### DRAFT: Reconcile, Plan, Sketch

**Step 0 — Reconcile (stage entry, run once, log `[MIGRATE]` in _LOG).** Bring a legacy paper up to this contract before any new work counts:

1. Create `_LOG_4-display.md` if missing.
2. If `4-display-probes.md` / `4-display-preview.txt` / an ASCII contact sheet exist: merge their content VERBATIM into `4-display.md` (plan rows → Display Map; probe entries → block evidence lines or `1-probes/` cards; contact-sheet sketches + `👉 {USER}:` notes → block sketches + `> USER:` lines), then delete the merged files.
3. If the existing `4-display.tex` carries `%% {USER}:` comments: migrate each VERBATIM to a `> USER:` line in the matching display block BEFORE the tex is first regenerated. Never lose a comment.
4. Legacy flat assets (`Figure/`, `Table/`, ...): give each a Display Map row (unitize now, or park with a `legacy` note and reconcile when its section is rewritten). No loose asset stays unmapped.

**Inbox.** Read `_DISPLAY_REQUEST.md` FIRST: every `status: requested` DR row enters this round — accept it (map row + block + scaffold; flip the row `accepted`) or decline it (write the reason back into the row; the requesting section sees it at CHECK). When a requested unit reaches `rendered`/`input-ready`, flip its row `done (unit: 0-displays/displayNN-slug/)` so the requesting section's probe can LINK it. Only THIS stage advances DR statuses.

**Plan.** Author or refresh `4-display.md` from the paper state. Group displays by PAPER SECTION in narrative order (one `-----` group per section, each display a `###` subsection inside it); open every group with its `venue expects:` line from the 2-venue.md blueprint, and state a GAP right there when a mandated unit has no subsection yet.

Illuminate first (per `../../../wiki/09-stage-illuminate.md`): present the current display set and ask -- which display is the hero figure? Which are main vs supplement? What visual forms (forest plot, panel, flow diagram, table)? Elicit taste before rendering anything. In a non-interactive run, never block on illuminate: record each unasked taste question as an explicit DRAFT ASSUMPTION in the md and present those assumptions at the gate alongside the open threads (the user overturns any of them with a ruling).

Inputs to read when present: `0-lifecycle/2-venue/2-venue.md` (FIRST — it fixes the display set, principle 9), `2-pitch/2-pitch.md`, `3-narrative/3-narrative.md`, existing `0-displays/`, upstream result paths the user names.

For each display, the block records **method candidates** — 2–3 genuinely different ways to make this display, each a lettered record line: form (forest / dot-whisker / panel / vector diagram / AI illustration / table), route (which renderer or task), and an empty output/verdict slot for PROBE to fill. A settled form needs only one row; for the hero/architecture figure, offer 3–5 framework options (pipeline chain, hub-and-spoke, layered stack, audit loop, feedback cycle) with pros/cons and expected reviewer friction. Sketch each display in ASCII with real numbers when known: sketches are free, renders are expensive — steer here, not after rendering.

**Scaffold.** Create a `displayNN-<slug>/` unit folder (templates below) for every map row that has none. One unit can hold one or many concrete results: a main figure, a table body, appendix variants, robustness previews, and the source needed to rebuild them.

**Probes.** Roll every probe this draft implies into the md's `Probes` section (shape in `ref/display-template.md`, mirroring seed/claims) — one `###` sub-item per probe: `S0` the cross-stage coverage sweep, `En` evidence-lane work (question SECTIONS to raise, tasks to run/extend; carry the `Detail:` pointer at the probe file), `Rn` render-lane dispatches (one per unfilled candidate line). Status each `▶ ready` or `✋ gated` on a NAMED open thread in a display subsection, so the user sees which ruling unblocks it. DRAFT proposes; it never executes an entry.

⛔ STOP. Present `4-display.md` — the map + sketches ARE the contact sheet, and the gate ask is TWO things: the open `> USER:` threads AND the Probes plan (what will run, what is gated on which thread). The user rules on threads, strikes entries ("skip En/Rn"), edits blocks directly. Their verb advances ([GATE] logged quoting the user; struck entries logged as skipped).

### PROBE: Evidence and Candidate Renders

Agent-only. Execute the `Probes` plan as the user approved it at the gate: a `✋` entry whose gating thread is still unruled stays blocked and is REPORTED at the end of the phase — never silently run, never silently dropped. After each entry, fill its `Outcome:` field (artifact path + one-line takeaway / self-assessment) and flip its status to `done`. Routing per `../../../wiki/11-delivery-need.md`; commissioning here is THIS stage's authority — the probe-display worker's no-commissioning ban binds section/narrative context, not the display stage acting on its own accepted units. This phase never hand-authors a figure or pastes numbers into `float.tex`.

**Step 0 — coverage sweep (S0).** Before the lanes, ask what the REST of the paper needs: read `3-narrative.md` beat display mentions, every `0-lifecycle/5-section-edit/*/<section>.md` (+ its `_DISPLAY_<section>.md` registry where present), and `\input{0-displays/...}` / `\ref{fig:...|tab:...}` uses in section files. Cross-check against the Display Map + inbox. Each unfiled need becomes a DR row in `_DISPLAY_REQUEST.md` filed on the section's behalf (`filed-by: display-probe sweep`), surfaced to the user via a `> CC:` note — accepting it into the map stays a DRAFT/user decision (only this stage advances DR statuses).

**Evidence lane — the numbers.** Every data-bearing display needs task-produced evidence on disk before anything renders:

```text
claim's status not settled yet         -> raise a question SECTION: /haipipe-paper probe "<need>"
                                          (a SECTION in 1-probes/; the stage's PROBE phase MATCHes it and
                                          dispatches only what MATCH cannot close. A stage NEVER dispatches
                                          an evidence agent itself.)
numbers not yet materialized           -> /haipipe-task-for-display <need>
```

`/haipipe-task-for-display` creates or extends a **paper-display task group** folder (e.g. `tasks/Z0N_Display_<topic>/`) whose task RENDERS from evidence (a landed QA file's anchors, a parser's `metrics.json`) into `source_data.csv` + `metrics.json` (+ optionally `assets/figure.pdf` / `assets/table-body.tex` directly). PHI-aware: raw data stays server-side; only aggregates land in the unit's `source/`. Prefer reusing an existing display task group (extend it with a new config) over creating a new one.

**Render lane — the visuals.** For each unfilled candidate row, dispatch the matching renderer skill. Every renderer writes into the unit per `ref/display-unit-output-contract.md`, in **candidate mode**: output to `candidates/<letter>-<form>.<ext>` + rebuild spec to `source/`; do NOT touch `assets/` or `float.tex` — promotion is REVISE's decision. (Single-candidate rows may render straight to `assets/`.)

| candidate form | dispatch |
|---|---|
| data plot (forest, dose-response, panel ...) | `/haipipe-paper-display-figure` — reads the task's `source_data.csv` / `metrics.json` ONLY |
| LaTeX table | `/haipipe-paper-display-table` — reads the task's aggregated CSV/JSON ONLY |
| editable vector diagram (research model, design, flow) | `/haipipe-paper-display-diagram` (FigureSpec JSON; elbow connectors + icons per CHECKLIST) |
| AI concept illustration (richest Figure 1) | `/haipipe-paper-display-illustration` (Codex bridge; fallback `/haipipe-paper-display-illustration-gemini`) |

The hard line survives: **numbers come from a task, never from the agent.** A data candidate whose source is not a task output is a defect; concept figures (no data) skip the evidence lane but a schematic/flow diagram is annotated with REAL Ns pulled from the data description.

After each dispatch, fill the candidate line in the md block: output path + a one-line self-assessment. Set block status to `candidates` (or `rendered` when a single route landed in `assets/`). Compile per-unit `preview.pdf` from the paper root with `pdflatex -interaction=nonstopmode`; preview success is NOT proof the display supports its claim.

### REVISE: Pick, Sync, Compile

1. **Pick winners.** For each block at `candidates`: compare renders against the takeaway + venue norms, record the decision IN the block (winner + one-line why per loser), promote the winner into `assets/`, move losers to `versions/`. A preference the user already voiced in a `> USER:` thread stands — never overrule it.
2. **Refresh units.** Write/refresh each unit's `float.tex` (caption + `\label{fig|tab:slug}` + paper-root-relative asset reference) and `README.md` (status, evidence source). Captions state the display's job without overclaiming.
3. **Sync.** Regenerate `4-display.tex` from the md (rules in Artifact Spec) and recompile `4-display.pdf` via the paper's `./1-compile.sh`, never per-file `pdflatex` for the gallery. A stale PDF is a defect; recompile after every edit without being asked.
4. **Consistency pass.** Labels match the map; numbers, datasets, baselines, panel letters synchronized across displays and text; resolution, axis labels, legend clarity, color accessibility.

### CHECK: Review, Audit, Gate

**Render review (builder ≠ judge).** Dispatch ONE independent subagent over the whole compiled set (so it can also judge flow and redundancy, not just units). Per display it reads `preview.pdf` / the gallery and returns: (a) render quality — no overflow, no overlap, no zero-width CIs, legible labels, not ugly; (b) the five-second test — does it convey its claim; (c) venue fit + narrative fit; (d) verdict `keep-main | keep-supplement | fix | demote | cut` + one sharp reason. Verdicts land in each md block (sync renders them small-font in the gallery). Apply `fix` items, re-sync, re-run on changed units.

**Audit.** Walk the audit questions: every map row has a concrete claim + evidence source; every display has a block and a unit (README + float.tex + current preview); captions match the actual asset/table body; each display supports the exact claim of its target section; main-vs-appendix placement right; no orphans (asset without map row, or map row without asset/float).

Route failures:

| Failure | Route |
|---------|-------|
| caption typo, stale label, path issue, gallery sizing | REVISE (fix md/unit, re-sync) |
| `float.tex` inlines pasted numbers (no task-produced asset) | PROBE: evidence lane |
| missing / weak render, candidate never tried | PROBE: render lane |
| unsupported claim | upstream: narrative or task/probe |
| wrong figure sequence, hero does not sell story | upstream: pitch or DRAFT |

**Insert.** Insert a ready display into a section file by adding `\input{0-displays/displayNN-slug/float.tex}`. Only status `input-ready` or better; place near the paragraph whose claim it supports; no duplicate input lines; update the map status to `inserted` after.

**Gate.** Walk `CHECKLIST.md` (this skill's folder). Present exit criteria per `../../../wiki/08-stage-gate.md`. User confirms before advancing.

## Principles

1. **No orphan displays.** Every figure/table must have a claim, source, section, and reader takeaway.
2. **Do not bake captions into image PDFs.** `figure.pdf` is the visual asset; `float.tex` owns caption, label, and `\includegraphics`.
3. **Make display blocks ready to input.** Section files should be able to use: `\input{0-displays/display01-hero/float.tex}`.
4. **Preview separately.** `preview.pdf` is a standalone review artifact built from the same `float.tex`. It lets humans and reviewers inspect the display without compiling the whole paper.
5. **Display is a contract layer.** Renderers and tasks create assets, but this skill records why each display exists and whether it still supports the story.
6. **Numbers come from a task, never from the agent.** A data display's asset is RENDERED from task-produced evidence (a probe verdict, a parser's `metrics.json`, `source_data.csv`), and the renderer's rebuild spec in `source/` points at that task output; `float.tex` only references the asset via `\includegraphics` or `\input`. Numbers typed directly into `float.tex` are a placeholder, not a display: route them through PROBE. A figure-bearing claim should be shown as a figure (forest, dose-response curve, panel), not only as a typed table.
7. **The md is the brain; the tex is a view.** `4-display.md` is the single working surface (map, blocks, candidates, sketches, threads, decisions); `4-display.tex` is regenerated wholesale by sync, `\input`s each `float.tex`, and compiles to the gallery PDF — the combined figures-and-tables view. Hand-editing the tex is a defect. Do NOT make a separate `preview-all` or contact-sheet file: the md's sketches ARE the contact sheet, the pdf is the compiled gallery. Compile from the paper ROOT so `0-displays/` paths resolve.
8. **Try different methods before committing.** Every non-trivial display carries 2–3 candidate rows (different forms/routes, including the illustration and diagram skills); PROBE renders them into `candidates/`, REVISE picks with a recorded why, losers keep history in `versions/`. Both display kinds follow the same rule: data-driven (parser → `metrics.json` → render; robust parser: factor-variable rows, leading-dot numbers, SE/CIs) and schematic/flow (study-flow, data-provenance, CONSORT — drawn by a diagram render annotated with REAL Ns, never hand-drawn).
9. **Venue-ALIGNED: couple to venue.** Read STATUS `venue`, then the paper's `0-lifecycle/2-venue/2-venue.md` FIRST: the Structural Blueprint's per-section `Display units` rows give the venue's standard display set and hero rule (e.g. Table 1 + STROBE cohort-flow for clinical, the research-model figure for MISQ, the main-result multi-panel for Nature/PNAS), and Writing Principles gives the display limits (figure count caps, table format, color guidelines). The `[primary]` claim's display is the hero. A venue change re-runs the display set. Fall back to the pack only when `2-venue.md` is absent (venue stage not yet run, or a pack-less venue): if `../../../_venue/playbook-<venue>` exists, consult its `README.md` section `-> Display`; if no pack exists either, proceed without venue inputs. Deep dives follow the `[source: ...]` tags in `2-venue.md` into `_venue/playbook-<slug>/<journal>/...`. If `2-venue.md`'s recorded pack commit is behind the current `_venue` HEAD, note "venue contract stale -- consider /haipipe-paper-venue refresh" but still use `2-venue.md` (never silently re-read packs).
10. **Commentary lives in 4-display.md; the gallery owns sizing.** Author/reviewer comments on a figure/table (preferences, "too thin," "park this," ordering) go ONLY into `4-display.md` as `> USER:` thread lines in that display's block, kept verbatim across iterations — never into a unit's files, never into the generated tex (units stay portable and comment-free). Gallery presentation knobs (width caps, float pinning, spacing) live in the md's gallery config and are emitted into the generated tex preamble — never pushed into a unit's `float.tex` or its source spec (units keep native size for the manuscript).

## Relationship to ARIS

ARIS treats figures/tables mostly as a production phase in Workflow 3:

```
paper-plan -> paper-figure -> paper-write
```

HAI-Pipe treats display as a manuscript layer that crosses story and evidence:

```
pitch -> narrative -> display -> section-edit
```

The difference matters. A display can fail because the plot is ugly, but it can also fail because the paper's claim, section role, or one-minute pitch changed.
