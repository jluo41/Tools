# Application Design Philosophy

An Application is a bounded conversion from evidence-backed understanding into an accepted delivery system.

```text
Task/Discovery evidence
  → Application-local Insight Pages
  → PageX-bound Design Pages
  → exact Artifact projections
  → deployment feedback
  → Task rerun and Insight refresh
```

## Two layers, two authorities

The Insights layer lives inside the Application because its questions exist to serve that Application. It uses Task authority because evidence does not become less empirical when its consumer is known.

The Design layer never opens Task/Discovery evidence. It receives settled Design Handoffs through PageX and owns applicability, composition, message roles, concrete content, and acceptance.

```text
Insights: Application Need → neutral Question → D → I → K → contextual W → Handoff
Design:   Handoff → principle → message/unit role → content → render → acceptance
```

## Anti-contamination rule

Application Need may name the blocked decision but not the preferred finding. D/I/K remain evidence-led. W may contextualize K for the Application's audience, behavior, venue, and risk. Final message copy begins only on a Design Page.

## Page grain

- One Brief per Application.
- One Insight Page per independently settleable insight question.
- Many Design Pages; default grain is one audience × behavior job × primary venue.
- One jointly reviewed message/touchpoint/panel/section per Design division.
- Artifact is projection-first; promote a Page only when the unit can pass/fail/deploy independently.

## Retargeting and iteration

Changing venue or audience normally reopens Design, not valid D/I/K. Changing source data reopens the dependent Insight trace; a changed Design Handoff then marks PageX-dependent Design and Artifact acceptance stale.

Deployment records are Task inputs, not self-validating design evidence. Task executes the measurement; the local Insight Page interprets it; Design decides what changes.
