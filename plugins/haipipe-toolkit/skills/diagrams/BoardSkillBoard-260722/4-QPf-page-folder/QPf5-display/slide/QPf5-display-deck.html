§1 · Same shape, new address

One display/ per page, one folder per unit

  ⟨page⟩/
    ⟨page⟩.md                     the page, on stage
    display/                      the plugin · discovery never enters
      ⟨PageID⟩-Display1-⟨slug⟩/   ONE rendered unit
        README.md      claim · kind · fragility · status
        intake/        caller-owned, provenance-bound values
          manifest.yaml
          inputs/      small approved extracts only
        recipe/        renderer-owned script, spec, receipts
        float.tex      caption + label + asset reference
        preview.tex    standalone wrapper inputting float.tex
        preview.pdf    compiled look, what the tab frames
        assets/        the WINNING render
        candidates/    pre-decision renders
        versions/      superseded variants, kept for history
      ⟨PageID⟩-Display2-⟨slug⟩/   the next unit, same shape

The folders split in two: intake/ and recipe/ are yours to write; assets/ and preview.pdf are rebuilt from them. A rebuild may replace the built half, and never touches the half you wrote.

Say the tree is copied from display-unit-output-contract.md word for word — resist any urge to improve it here. The one page-side change is the address: the unit sits inside the page's own display/ folder, so when the page moves, its figures move with it.

§2 · The tab, and pointing

Every unit shows as a card, and a sentence can point at it

🖼 One card each

The right pane frames each unit's preview.pdf (body.py ccpdf) with its README status. An empty display/ is an empty state, not an error.

🔄 Rebuild only

🔄 builds preview.pdf again from preview.tex. It never reruns the recipe, never changes the inputs, and never changes a yes.

Id becomes a button

Name a unit's id in plain text and that id turns into a small button; click it and the card opens with its picture and its yes-or-no state.

A machine's door

A > Display: line under a sentence, beside > Citation: and > Value: — so a program adds evidence without editing a person's words.

You may point at a unit that has no picture yet; the button then says a drawing is still owed. Exports carry the evidence too — the LaTeX PDF prints a named unit as a real figure right after its paragraph, and Word inserts the picture with its caption plus a 🖼 comment note.

Emphasize that a unit is EVIDENCE, which is why it attaches to a sentence the same way a citation or a value does. The two forms exist for two writers: the inline id for people, the > Display: line for machines.

§3 · Three hands, one yes

Drawing skills fill the folder, a person clicks the yes

  • 🎨 renderer skills — -table, -figure, -diagram, -illustration write recipe/ · assets/ · preview.pdf
  • 🧑 a person — rules intake/ and ticks accepted:
  • 🖼 the pane — shows everything · writes NOTHING
  • ✅ in accepted: means a person looked at one exact picture and said yes
  • A machine that ticks it has faked a judgment, not saved time — so no machine may tick it

The drawing skills already belong to the display family; this page adds none of its own.

This is the one rule on the page with teeth — say it plainly and don't soften it. The pane being read-only by build, not by policy, is what makes the rule enforceable.

§3 · One door, five renderers

🚪 haipipe-display — say the ask, it picks the renderer

  🎲 data-driven · needs a ruled intake/ of numbers
     📊 -table         CSV/JSON  ▶ booktabs · recipe = the spec
     📈 -figure        results   ▶ plot     · recipe = the script
  🧠 concept-driven · the intake is a spec, not numbers
     📐 -diagram       FigureSpec JSON ▶ editable SVG
     ✒️ -tex           .tex recipe ▶ vector PDF · a person writes it
     🎨 -illustration  image-gen prompt ▶ concept figure

A data-driven skill may not go back to the raw data — it reads only the small approved copy in intake/. ✒️ earns its row because it is written in TeX itself, so it picks up the document's fonts and math and float.tex can pull it in directly; named after the MECHANISM, haipipe-display-tex covers a TikZ figure, an algorithm block, and a display equation alike (JL 260816). It still owes a compiled assets/figure.pdf.

Both units on this page were drawn by hand in TeX, so the ✒️ row is not hypothetical. Close by noting redraw depends on kind: a python figure reruns its script, a diagram redraws from its spec, an AI picture replays its saved prompt.

§4 · The order of the work

Five steps — ① ③ ⑤ are a person's, ② ④ are the machine's

  ① INTAKE   🧑 the caller fills intake/: manifest.yaml + small
                approved extracts, every value provenance-bound
  ② RENDER   the matching renderer runs via task-for-display;
                it fills recipe/ + candidates/
  ③ PICK     🧑 a person picks the winner into assets/; losers
                stay in candidates/ or versions/
  ④ BUILD    preview.tex compiles to preview.pdf; --check
                reports a stale unit instead of hiding it
  ⑤ ACCEPT   🧑 a person reads the render and ticks accepted:

Nothing is drawn before a person approves the numbers. If the inputs change, the work runs forward again from ② to ⑤ and the old yes drops back to ⬜, because the picture a person agreed to no longer exists. Step ①'s numbers come from a PROBE (QPf9) → orchestrator → haipipe-task run → the answer at <task-folder>/QA/<n>-<slug>.md; intake/manifest.yaml cites that holder by id, never by path, and never types a number by hand.

Ask once, point at it twice — that's QPf5-Display2's whole claim. The slides plugin on QPf3 already proves the id-to-path lookup works, so its template holds no digits at all and a hand-typed number has nowhere to live.
