# Q-consumer · PP02-phone-column-count

## C3.P1.B4 · "About 390 CSS pixels at 13px metrics is roughly 46 columns, and Claude's frames are drawn for far more"
Both halves of the comparison are estimates. "About" and "roughly" carry the near
side, no device is named, and no fit computation is shown; "far more" is the far
side, with no number at all for the width the box art actually needs. The State
row for A3.1 repeats the same estimate as though it were the measurement
("The measurement is in: about 390 CSS pixels …"), so the page's own record of
having measured is the estimate itself.

## Stake
What this page loses: A3.1, whose Done-when is "Content 3 carries the width below
which the raw grid is dropped rather than shrunk, and names the view that takes
its place". That width IS this number. Below it the raw grid is the defect and
only a reflowing view fits; above it, polishing the grid pays.

The 📐 Decision Now row picks the phone's entire form (A: composer plus read-only
pane · B: the smooth pane · C: keep the grid, fix input only) and reads
differently on either side of that line, so an estimate ten columns off moves a
ruling only JL can make.
