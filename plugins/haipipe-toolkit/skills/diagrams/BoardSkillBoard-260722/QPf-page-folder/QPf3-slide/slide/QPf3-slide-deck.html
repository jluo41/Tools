The home · derived, never registered

Existence of the file is the whole state

📄 One path per page

A folded page owns slide/, and the deck's name is the page stem plus -deck.html.

🔑 Derived, not listed

Both doors compute the path from the page they are on, the way Draw derives its owner.

🕳 HEAD and know

No manifest row, no registry — nothing keeps a list that could drift.

When the file is absent the surfaces say so and offer the button; nothing generates a deck behind your back.

The design move here is refusing to keep state. There is no row anywhere saying "this page has a deck" — you HEAD the derived path and you know. That means the surfaces can never disagree with the disk, because there is nothing to fall out of sync.

The two doors · one loader behind both

Where a deck opens

🚪 The Slides tab

In the shell beside Chat and Draw, with the ✨ bar riding above the frame.

🚪 The page's 🎞 panel

A resizable right split, with ✨ regenerate in its header.

🔑 ?plain

Without it, the deck comes back wearing the operating shell.

🔄 Cache-busted, always

A freshly written deck appears on the next click; a stale iframe can never survive its file.

Two doors, but deliberately one behavior: both HEAD the derived path and either show the saved deck or point you at the sparkle button. The cache-busting matters more than it looks — regeneration overwrites in place, so the loader has to guarantee the next click shows the new file.

✨ Regenerate · one click, one authored deck

The loop, and its guardrails

  • ✨ click posts to /_board/autodeck; live/autodeck.py runs claude -p on the page's .md, ⏱ a few minutes.
  • The ask box is optional — empty means "present the page's argument"; a typed ask steers the emphasis.
  • The <head> is computed server-side from real paths, so the model's freedom starts at <body> and a deck can never 404 its own stylesheets.
  • Validation before write: a complete document, at least three slides, the asset links present — or the deck is refused and the old file stands.
  • Regeneration always overwrites, so a lasting correction belongs on the PAGE, which is what every regeneration reads.
This is the heart of the contract. The server owns everything that must be correct — the head, the links, the validation gate — and the model owns everything editorial, from body onward. And the last point is the discipline: don't hand-fix a deck, fix the page, because the page is the only thing the button ever reads.

What a deck is · html-ppt's shell, this board's voice

Six to nine slides on a shared shell

🎨 One theme, shared

academic-report by default, T cycles the short gallery; the board contributes no CSS of its own.

⌨️ Full runtime

← → move, F fullscreen, O overview, S presenter mode.

🗣 Notes on every slide

Speaker guidance rides along, surfaced by S — a talk, not a caption reel.

🛡 Survives blocked scripts

No data-js stamp, and CSS flattens the deck to one fragment-picked slide — it still reads.

Decks link at the skill's assets by relative path, nothing copied — a theme improvement reaches every deck with no rebuild.

The html-ppt skill owns everything a deck looks like; this board only supplies the words. Because assets are linked, not copied, improving a theme once upgrades every deck ever written. And the no-JS fallback means even a locked-down viewer gets a readable talk, one slide at a time.
