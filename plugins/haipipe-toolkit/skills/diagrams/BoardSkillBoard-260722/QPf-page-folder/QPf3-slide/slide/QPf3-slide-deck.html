This is a settled design — the surface is live end to end, and all four aims closed on 260815. The question we answered: where does a page's talk live, and how does it stay fresh? The answer is a single derived file and a single button.

1 · The home

Derived, never registered

📄 ⟨page⟩/slide/⟨page⟩-deck.html
🔑 derived from the page's own path, the way Draw derives its owner
🕳 no manifest row, no registry: HEAD the path and you know

A folded page owns its slide/ folder; both doors derive this path from the page they are on, so nothing keeps a list that could drift. Absent file? The surfaces say so and offer the button — nothing generates behind your back.

The key move here is that existence of the file is the whole state. There's no database row to go stale, no registry to sweep. If you can HEAD the path, you know everything. This mirrors how the Draw plugin derives its owner, so the pattern is already familiar.

2 · The two doors

One loader behind both

🚪 The 🎞 Slides tab

The shell tab beside Chat and Draw, with the ✨ bar riding above the frame.

🚪 The page's 🎞 panel

A resizable right split, with ✨ regenerate in its header.

🔑 ?plain

Or the deck comes back wearing the operating shell.

Every load is cache-busted, so a freshly written deck appears on the next click and a stale iframe can never survive its file.

Two doors, same behavior: both HEAD the derived path and show the saved deck, or a pointer to the sparkle button when none exists. Cache-busting matters more than it sounds — without it, the button would write a new deck and you'd keep watching the old one.

3 · ✨ Regenerate

One click, one authored deck

✨ click ──▶ POST /_board/autodeck {file, prompt?}
         ──▶ live/autodeck.py runs claude -p on the page's .md
         ──▶ 💾 slide/⟨page⟩-deck.html replaced ──▶ frame reloads
⏱ a few minutes · the status word says so while it thinks

The ask box is optional: empty means present the page's argument; a typed ask steers the talk's emphasis. Regeneration always overwrites — a lasting correction belongs on the PAGE, which is what every regeneration reads.

This is the whole loop. Note where the trust boundary sits: the head with its asset hops is computed server-side from real paths, so the model's freedom starts at the body and a generated deck can never 404 its own stylesheets. And overwrite-always is a feature — it forces corrections upstream onto the page itself.

3 · The write, guarded

Validated before it lands

  • 🛡 A complete document, or the deck is refused
  • 🛡 At least three slides, or the deck is refused
  • 🛡 The asset links present, or the deck is refused
  • 💾 On refusal, the old file stands untouched

👀 And no acceptance gate after the write: CC ruled under JL's delegation ("check it yourself") — the presenter is responsible for having read what they present, and regeneration is one click.

The server validates before writing, so a broken generation can't destroy a good deck. The no-gate ruling deserves a beat: a review gate would add friction with no consumer, and it's reversible the day a deck misleads someone. One-click regeneration is the safety valve.

4 · What a deck is

html-ppt's shell, this board's voice

🎨 Six to nine slides

A cover, a closer, and distilled middles built from the page's own emoji, numbers, and quoted rulings.

🗣 Notes on every slide

Speaker guidance surfaced by S; ← → move, F fullscreen, O overview, T cycles themes.

🔗 Linked, never copied

Every deck links at the html-ppt skill's assets by relative path — a theme improvement reaches every deck with no rebuild.

🛡 Reads without scripts

Scripts blocked? The data-js stamp is absent and CSS flattens the deck to one fragment-picked slide.

The html-ppt skill owns everything a deck looks like; the board contributes no CSS of its own. That separation is what makes the theme a shared asset — fix the academic-report style once and every deck on the board inherits it on the next load.
