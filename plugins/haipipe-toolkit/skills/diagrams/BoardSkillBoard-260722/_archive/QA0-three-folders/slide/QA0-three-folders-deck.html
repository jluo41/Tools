Three folders,
three kinds of truth

The skill family that SHIPS, the board where it IS ARGUED, and everything it RENDERS — and why mixing them up costs a decision, a history, or an edit

QA0-three-folders · AI-generated deck, 260815
The opening problem: all three folders are casually called "the Board", but each carries a different kind of truth. This deck names them, draws the movements between them, and ends on the one-line test that keeps them honest.

The map

Ships · argued · rendered

⚙️ ① the family

skills/board/ — reusable procedure, read by a runtime. The door, the engine, the specs, the agents, each on its own version clock

🗂 ② its board

BoardSkillBoard-260722/ — the rulings that PRODUCED the family, read by people. One folder per group, board.md the manifest

📤 ③ the rendered

every board/ site the family builds — generated output, read by anyone, owned by no one. The next build erases any hand edit

② is itself one of ③'s inputs — it is numbered apart only because it is the one board whose CONTENT this family owns.

One number per folder on disk: the family is one folder and one roster entry, so subskills nest inside it rather than earning peer numbers. That collapse — seven numbers down to three — was JL's 260731 ruling.

Lifetime decides

Each kind breaks in its own way

kind          lives              breaks how
⚙️ ships      while anyone       a design argument leaks in — the skill
              uses it            cannot ship without its own history
🗂 argued     until the board    a runtime starts reading it — an OPEN
              closes             question becomes a dependency
📤 rendered   until the next     someone hand-edits it — the edit
              build              vanishes silently

Putting a file in the wrong layer leaves a decision nonbinding, ships working history as law, or loses an edit on the next build.

The distinction is not aesthetic. Each failure mode on this slide has a concrete victim: a nonbinding decision, history shipped as law, an edit lost silently. The model succeeds when a reader can place any new file without guessing.

The crossings

Three movements are legal

🎓 ② graduates → ①

a page reaches ✅ and its Law is COPIED into the owning unit. The page stays; the skill gains the rule

🏭 ① renders → ② ③

build.py reads a board folder, writes its board/ site. The renderer reads FORM, never meaning

✍️ ① writes back → ② ③

serve.py turns a click into one line of markdown in a page — always the .md, never the .html

Inside ①, units stay separable: routing reads board.md and each page's title line, and never imports the engine's src/.

The fourth movement on the page — separability inside the family — is what makes subskills real: two units that ship on their own clocks. If routing ever imports haipipe-board/src/, they are one skill wearing two folders.

The two ✗

Delete the board; the family still runs

✗ ① → ②

the family may never depend on the board that designs it — no runtime reads a Q page

✗ anything → board/

it is output; the next build erases you. Nothing is ever hand-written into a generated site

The whole test is one line: delete ② and every skill in ① still runs.

This is the slide to slow down on. The deletability test is the page's reason to exist, and it is also the part not yet enforced: check.py can prove a Law graduated, but nothing yet proves no shipped file cites a Q page.

Admission

A unit inside ①, never a folder beside it

  • A unit earns its own directory with its own trigger, its own contract, and its own version
  • That test admitted haipipe-board-index on 260730 — and the admission was reversed on 260802, when three of its five verbs turned out to be other units' work written twice
  • Membership on the board side is by PATH, never registration: moving a page is a pure git mv
The reversal matters more than the admission: the trigger-contract-version test cannot detect duplicated work, only a person reading the verbs can. The index folded into routing for that reason.

Scope

One server, every board under the SPACE

  • A board folder is the unit of CONTENT, not the unit of SERVING
  • serve.py's --root is the repo root, so every board beneath it is live at once and none owns the process
  • Terminals key on the sha1 of a page's absolute path — two boards' QD3 can never collide
  • The bite: anything shared (assets, the engine) changes every board at once, so a change checked against one board has not been checked — QF1's problem
Neither obvious alternative runs: not one server per board (opening a second board costs nothing), not one server per several SPACEs (only port 5599 is forwarded — QE6's decision, not this page's).
