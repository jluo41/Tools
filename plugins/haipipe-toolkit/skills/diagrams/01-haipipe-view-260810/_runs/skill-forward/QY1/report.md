## Inferences made (not stated verbatim in either skill doc)

1. **Which two Probes to bind.** `tasks/QV1-agreeableness/QA/` contains only one dedicated QA file (`1-bound-source-count.md`), and no sibling task folder on this board carries a second agreeableness-evidence Probe. I reused QBt1's own bound Probes 2 (`2-observable-signal.md`) and 3 (`3-measurement-boundary.md`) — both genuinely `state: answered` records — as QY1's two QA-probe inputs, copying them byte-identical into `input/QA-probes/`. This is documented in QY1's own Log rather than silently done.
2. **Consumer binding without editing the target.** Neither skill doc states how `resolve_from()` walks paths. Reading `scripts/view.py` showed it checks `unit/candidate` first, then walks every ancestor of the View's resource folder looking for `ancestor/candidate`. Since `QS-consumers/S-Main-4-results.md` sits at the board root, four levels above `views/QY1-for-view/`, the relative path `../../QS-consumers/S-Main-4-results.md` resolves correctly without copying or modifying the target file. Unlike `input.qa_probes`/`input.sources`, `validate()` places no `path.relative_to(unit)` constraint on Consumer targets, so an outside-the-View real Page link is legal by the checker's own rules — I did not need to fall back to a review-only cross-reference.
3. **Table Display rendering.** The skill doc says "dispatch craft by kind to the existing table... renderer" but does not name a script. I followed QBt1-Display1's own pattern (`assets/table.tex` wrapped by `float.tex`, referenced from the Page as `output/.../preview.png`), and rendered it myself: a small `standalone.tex` wrapping `\input{assets/table.tex}`, compiled with `xelatex`, then `pdftoppm -png -r 200` for the PNG and a direct copy of the compiled PDF for `preview.pdf`. No placeholder or empty file was used — both previews are real, non-empty, and separately verified (`file` reports valid PNG/PDF).
4. **`view.py` has evolved since the QZ1/QV7/QV9 runs recorded in this board's history.** Those older reports show `input/probes/` (singular, no "QA-"), a `--target` flag on `build`, and a separate `packages/` output tree. The current script (read directly, not assumed) uses `input/QA-probes/` and writes review output straight into `<unit>/build/review/` with no `--target` flag; there is no separate package/export step in this version. I followed the current script's actual behavior, not the older reports' commands.
5. **Q reference syntax.** The page-for-view contract shows `[Q-View-1]`-style checked-number syntax only by example (QBt1). I mirrored the exact same bracket convention QBt1 used for its own task QA-bank reference, since neither skill doc spells out the syntax independently.
