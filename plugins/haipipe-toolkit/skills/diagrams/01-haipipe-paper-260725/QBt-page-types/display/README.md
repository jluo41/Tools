# display/ — the authoring side of the UNIT shape

One folder per display page, named for the page that owns it. This is where a
unit is worked on; `_fixture/displays/` is where it is shipped, and that side is
generated and never hand-edited.

```
QBt-page-types/                       the STAGE
├── display/<page>/                   HERE. seven parts, all authored
│   ├── source/       the recipe: gen_*.py · source_data.csv · paper_plot_style.py
│   ├── candidates/   the options that lost, kept with their reason
│   ├── assets/       the SELECTED artifact float.tex points at
│   ├── float.tex     the figure env, caption and label
│   ├── preview.tex   standalone wrapper, compiled from the paper root
│   ├── preview.pdf   the render a person judges at rung ④
│   ├── preview.png   the same render, embeddable on the page
│   └── README.md     Reader Takeaway · Claim Supported · Evidence Source ·
│                     Placement · Caption Job · Fragility · Status
└── _fixture/displays/<page>/         SHIPPED. float.tex + assets/, nothing else
```

## Commands

All three tools live in the board engine and take this stage as an argument.
There is no copy of them here, and that is the point: the specimen has to run
the same file the real papers run, or it proves nothing about them.

```
 python3 $SKILLS/board/haipipe-board/cli/build-displays.py <stage>          ship to _fixture/displays/
 python3 $SKILLS/board/haipipe-board/cli/build-displays.py <stage> --check  non-zero if stale
 python3 $SKILLS/board/haipipe-board/cli/display-report.py <stage>          the display -> section map
 python3 $SKILLS/board/haipipe-board/cli/asset-manifest.py <stage>          each unit's assets/README.md
```

Rebuild a unit's artifact first, then ship:

```
 python3 display/QBt3-for-display/source/gen_display_pipeline.py               -> assets/
 python3 display/QBt3-for-display/source/gen_display_pipeline.py --candidate A -> candidates/
```

## What is different here from a real paper

One thing only. A real paper's stage sits INSIDE the paper root, so it ships
UP, to `../../displays/`. This stage has no paper above it, so it carries its
own root at `_fixture/` and ships DOWN. Every path in `float.tex` is still
written relative to the paper root, which is why the authoring path here reads
`../display/<page>/` where a real one reads `0-lifecycle/S05-display/display/<page>/`.

## The unit-to-label map

```
# --- display-map:begin (generated) ---
  ONE UNIT, ONE LABEL. Generated by board/haipipe-board/cli/build-displays.py.
  Do not hand-edit: the unit is its folder name, which is also its page name,
  and the label is the \label{} inside that unit's float.tex. Nothing else
  declares either, so nothing else should restate them.

  WHICH NAME TO WRITE, in a markdown page:
    talking ABOUT the display  ->  the UNIT name, which renders as the evidence card
    pointing FROM a sentence   ->  \ref{tab:...}, because that line becomes manuscript
  A `> Display:` lane writes BOTH, unit first, then the pointer it binds.

  unit              kind  label                            reaches master
  ----------------  ----  -------------------------------- --------------
  QBt3-for-display  fig   fig:display-pipeline             yes
# --- display-map:end ---
```
