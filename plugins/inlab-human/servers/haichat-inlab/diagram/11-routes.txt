─§ labeling_api ────────────────────────────────────────────────────

  GET    /api/labeling/dimensions
  GET    /api/labeling/corpora
         The selectable corpora for this dataset — one per built labeling universe, each carrying
         the dimensions bound to it. This is the layer BETWEEN cases and labeling: you pick a
         corpus, then a dimension on it.
  GET    /api/labeling/{dim}
  GET    /api/labeling/{dim}/guideline/{version}
  POST   /api/labeling/{dim}/decision
         The one write: the researcher's adjudication, appended to an audit file of its own. The
         panel's artifacts (gallery, guideline) are NEVER touched here — folding a decision into the
         gallery is the gallery-keeper's job, through the sl loop.
  GET    /api/cases
         Cases for the chosen data type, best source first: caseset the dataset's cooked case sets
         (INLAB_CASE_STORE): one case per trigger moment, with facets text-row no case set: one case
         per record row that holds prose (a dialogue, a review, a note) none no case set and no
         prose rows (a timeline): no cases, and the view says why and, with no dataset at all, the
         labeling-corpus browse.

─§ message_api ─────────────────────────────────────────────────────

  GET    /api/personas
         The styles a clinician can pick: message personas + judge rubrics.
  POST   /api/message
         ② compose — forecast in, patient message out. Never sees `observed`.
  POST   /api/judge
         ③ LLM-as-judge — scores the MESSAGE, not the forecast. Also blind.
  POST   /api/feedback
         ④ the human's verdict. NOT a run: append-only, attributed, never replaced — this is the
         clinical-expert record the LLM judge is measured against.
  GET    /api/runrecord
         The whole chain for one run: prediction ▸ message ▸ judge ▸ feedback.
