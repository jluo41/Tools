## 我们怎样建立这个概念

从一个实际目标开始：“哪个模型更合适？”

1. 先明确交付要回答的问题，以及回答所需的证据。误差更低是一项证据，是否更合适还取决于目标与其他约束。
2. 找到需要独立讨论和修改的内容。例如结论 S17：“模型 A 的误差更低。”把这样的内容叫作 Brick。
3. 给内容确定归属。Project、Theme 和 BJTR 组织工作；内容、证据、评论记录在各自的源文件里保存。Run 产生或修改成果，Brick 不必成为 Run 的下一级。
4. 围绕阅读和判断安排 UI。同一个 Brick 可以在 Report 和 Review 出现，共用身份与记录。
5. 保留变化。内容有版本，确认和评价针对具体版本；更换页面位置不应更换内容身份。
6. 安排推进方式。AI 在授权范围内生成、核对、改进；不确定的问题和关键取舍带着依据交给人。
7. 在交付前检查整体。除了每个局部，问题、证据、结论之间的关系也必须成立。
8. 留下推理过程。Session 的 episode 记录一次推进的目标、改变和理由；Studio topic 持续积累方案、决定和未决问题。

这里的“一体”是有归属、有关系、可追溯的工作内容。“两面”是它在文件与页面中的两种呈现和访问方式。

## 图的边界

- 图 01 的目录树是常见归属的示意；不同 Theme 的 Run 位置与类型遵循各自契约。
- 图 02 展示拟议的身份与版本行为；当前共享卡片尚未全部实现这种语义。
- 图 03 是协作过程的概括，不是把所有 Theme 规定成相同流程。
- Report 与 Review 示意两种阅读方式，不是在此新增产品导航。
- 图 03 的 Session 长条表示贯穿工作过程的记录；一个交付可能跨多个 Session。
