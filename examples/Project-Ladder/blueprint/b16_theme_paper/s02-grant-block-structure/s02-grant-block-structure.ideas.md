# Grant Block Structure · open choices

## How should groups reference records?

- Explicit group membership fields on Job, Task and Studio topic faces.
- A Block-owned grouping index that points to those records.

Leaning: one explicit source for membership, reused by the shared renderer. Display meaningful Grant names such as Story → Research case → Aims → Specific aims. Folder numbers identify records; they do not replace their names or define their group. The examples are design instances until real records are bound.

## How much detail should the Skills view show?

Structure, Draw, Examples and Skills are the top views of this same structure Studio. Structure holds Jobs and Studio organization as left entries; Draw shows the named Grant structure; Examples uses actual Block names only when bound to real Blocks. Skills offers the relevant skill entries on the left and the selected function's inputs, outputs, workflow and checks on the right. Functions stay within their owning skill entry. The choice left open is how much detail to show before selecting a function, not whether to create more Studios.


## Which missing type contracts should we define?

The current Paper reader identifies Writing Version and legacy display/value/citation branches from names; it does not expose explicit new Grant Job types. Keep Job Type / Job Name / Task Type / Task Name separate from both group fields. Reuse `draft` for prose where its owner applies. Legacy Paper value faces use unregistered `value`, while citation faces use `evidence` for a purpose that conflicts with the registered numeric executor. Grant Values, Citations and Checks therefore retain unresolved Task mappings; a consumer-side evidence contract and explicit routing must be settled before scaffolding. The Grant names here remain proposed targets, not current records. The final figure asset is not the registered upstream `display` input Task. Story, consolidated Evidence and Presentation Job contracts, plus final-asset, packaging and media-production Task contracts, remain proposed. Roles and formats do not become types by renaming them.

## Which Studio discussions deserve their own record?

- Research design can collect Aims and rationale or Methods and feasibility.
- Communication can collect Application narrative or Pitch design.

Leaning: create a named topic only for an open question with a distinct delivery. These are proposed discussion names, not required folders or live records; their group membership remains metadata.

## How should one call determine the application Tasks?

- A call profile creates only the required sections and attachments.
- A shared Grant starter creates a broad menu, then the writer removes unused parts.

Leaning: a call profile with explicit overrides. The unresolved part is how to carry a changed call forward without overwriting authored text.

## When does a retargeted application need another Block?

- Keep a new Writing Job when the research case remains the same.
- Create a linked Grant Block when the aims, team or project boundary become materially different.

Leaning: preserve a shared Block for the same research case; use an explicit decision when the boundary changes.

## How should Idea feed Grant?

- Extend the existing handoff contract to identify a Grant destination.
- Add a Grant adapter which consumes the same immutable scientific packet.

Leaning: reuse the packet and selection authority, with a destination adapter. Grant support must not silently treat a Paper-only contract as already implemented.

## What remains shared when the call changes?

Story, verified Evidence and reusable Display sources retain their identities. Each Writing Job pins the source revisions it uses; the call's required fields and the application's wording belong to that version. Proposed results stay with the research approach, outside the returned evidence register.
