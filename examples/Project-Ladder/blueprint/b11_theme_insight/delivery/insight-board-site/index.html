how a plugin is designed

A plugin is a harness for an agent's work

It has two sides, and each side has a Folder System and a UI System. The Work side is what the agent makes and a person reads. The Define side is the plugin itself: its skills, servers and blueprints, seen on the workbench page of its blueprint Block.

Two sides, four parts

The principle

  1. Work Folder. Decide what folders the work is stored in: each Block's Jobs, Studio topics and Chats.
  2. Work UI. Decide how a page shows those folders. A page shows nothing that is not on disk.
  3. Define Folder. skills/, servers/ and examples/: what an agent knows, the page code, and the plugin's own Block.
  4. Define UI. The blueprint Block's workbench page: each level's views and buttons, each linked to an example page.
  5. The map. Every work folder kind has a page part; every page part draws a work folder.
  6. The rule. A change lands everywhere at once: skill contract, page code, blueprint definition, and a test that it is drawn.

How it works

  • Using it. The skills write the Work Folder, through their gates and checks. The page code reads those folders each time a page opens, so the Work UI follows them and keeps no copy.
  • Changing it. The change is worked in the blueprint Block and seen on its page; the skills and the page code change with it. Work already on disk is read by the new code, or carried over by a script.

Where to start

WorkBlock and chat folders, and the pages that show them. DefineSkills, servers and the blueprint Block, and the page that shows the UI's definition. The MapFolder, Element and Session views, and how each reaches the other two.
